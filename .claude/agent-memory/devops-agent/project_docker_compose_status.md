Root `docker-compose.yml` (at `c:\zzz-shubham\MTS\docker-compose.yml`) was built 2026-09-10, fulfilling Phase 0's originally-blocking "Docker Compose for local dev" task that had never actually been done (Phase 0 shipped on a one-off bare `tiro-mysql` container instead — see [[project-mysql-workaround-origin]]).

**Live**: `redis` (7-alpine, :6379), `meilisearch` (`getmeili/meilisearch:v1.53.2`, :7700, real `MEILI_MASTER_KEY`), `mailpit` (:1025 smtp / :8025 UI, not yet wired into `backend/.env`'s `MAIL_MAILER`). Start with `docker compose up -d redis meilisearch mailpit` (or just `docker compose up -d` — see below, this is now actually safe).

**Staged AND profile-gated** (`profiles: [staged]`, added 2026-09-11): `mysql`, `app` (Laravel/Sail runtime), `node` (Next.js). All three would conflict on host ports already held by pre-existing live processes (bare `tiro-mysql` on :3306, native `php artisan serve` on :8000, native `next dev` on :3000). Because of the profile gate, `docker compose up -d` (bare, no args) now only starts the three LIVE services above — it will NOT touch mysql/app/node. To run any of the staged three, `--profile staged` is required: `docker compose --profile staged up -d mysql`. Verified 2026-09-11 via `docker compose config --services` (no profile → only mailpit/meilisearch/redis listed; `--profile staged` → all 6 listed).

**2026-09-11 INCIDENT — what actually happened:** The `mysql` service started anyway, auto-named `mts-mysql-1` by Compose's default `<project>-<service>-<n>` naming (Compose project name "mts" derives from the `MTS` root folder). It raced the real `tiro-mysql` bare container for host port 3306. Root cause, confirmed by direct evidence (not assumption):
- `docker ps -a` after the incident showed no `mts-app-1`/`mts-node-1` container ever existed — ruling out a bare `docker compose up` with no service args, and ruling out `app`/`node`'s `depends_on: mysql` cascading it in. `mysql` was targeted directly, most likely via `docker compose up -d mysql` — the exact command this file's own header quotes as a *future, manual* cutover step, run out of that context.
- `docker logs mts-mysql-1` showed a clean `Received SHUTDOWN from user <via user signal>` at 06:19:53 — a deliberate stop (`docker stop`/similar), not a crash or a lost port race. `tiro-mysql`'s `StartedAt` was 06:19:56, 3 seconds later, and its `RestartPolicy` is `no` (confirmed via `docker inspect`, matching [[project-mysql-workaround-origin]]) — so this was a targeted manual recovery action (stop the interloper, then explicitly start the real one), not a Docker-Desktop bulk "restart previously running containers" event. A peer agent relayed a theory that Docker Desktop's restart silently handed the port from `mts-mysql-1` to `tiro-mysql` mid-session — the container logs/timestamps directly contradict that framing; ports don't get silently reassigned between two already-running containers, and nothing else on the host restarted at that moment. Both accounts agree on the structural point that matters: two separate containers, same `tiro` database name, same root password, same port, by design (see below) — so a client couldn't have told them apart even without any port race at all.
- The `mysql` service was deliberately built (2026-09-10) to mirror `tiro-mysql`'s credentials/database name/port exactly, "so the eventual cutover is a swap, not a reconfiguration" — meaning it was never actually isolated from `tiro-mysql` even before any collision; whichever container currently holds the port receives all traffic from any client using `backend/.env`'s `DB_HOST=127.0.0.1:3306` credentials.
- Separately, `backend-tester` hit a related-but-distinct problem: `backend/phpunit.xml` hardcoded one fixed `DB_DATABASE=tiro_testing` for every Pest run on the shared `tiro-mysql` server — concurrent full-suite runs (not just the mysql-service/tiro-mysql port collision above) were silently sharing that one schema. This is a genuinely separate bug from the port race, not the same incident wearing two names.

**Fix, 2026-09-11:**
1. `mysql`/`app`/`node` now carry `profiles: [staged]` — closes the "ran the documented future cutover command out of context" hole completely; none of the three can start without explicit `--profile staged`.
2. Orphaned `mts-mysql-1` container and its `mts_mysql-data` volume were removed (`docker rm`/`docker volume rm`) — confirmed gone via `docker ps -a`/`docker volume ls`.
3. Test-suite concurrency fixed independently via `backend/scripts/test-db.sh` (per-run ephemeral schema) — see [[project-test-db-isolation]] for that mechanism and a non-obvious `--env` flag gotcha discovered while building it.
4. `backend/.env.example` was also found stale (still `DB_CONNECTION=sqlite`, contradicting the real MySQL setup) and corrected to match `backend/.env`'s actual mysql config.

**Why (original 2026-09-10 reasoning, still valid):** Meilisearch was the actually-urgent, blocking need (Phase 1 catalogue/search, Scout wiring) and had zero conflict risk as a net-new service. Redis and Mailpit were free wins alongside it. Mysql/app/node completing the "real compose" picture was valuable but not urgent, and forcing it same-day meant either breaking live sessions or picking non-standard ports that would fragment the setup further — deferred as a deliberate follow-up, which is exactly the follow-up that caused the 2026-09-11 incident once the deferred definition got run out of its documented context.

**How to apply:** Don't remove `profiles: [staged]` from `mysql`/`app`/`node` without a deliberate, coordinated cutover (see the header's cutover steps in `docker-compose.yml` itself, now updated to include `--profile staged` and a `docker ps` check for `tiro-mysql` first). If this status has changed (mysql/app/node actually adopted), verify current `docker compose ps`/`docker ps` state before trusting this snapshot — this memory will go stale once that cutover actually happens.
