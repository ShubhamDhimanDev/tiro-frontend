Built 2026-09-11 in response to two real DB-collision incidents in one testing round (see [[project-docker-compose-status]] for the fuller incident). `backend/phpunit.xml` used to hardcode one fixed `DB_DATABASE=tiro_testing` for every Pest run on the shared `tiro-mysql` container — concurrent full-suite runs from different agents silently shared that one schema.

**What was built:** `backend/scripts/test-db.sh` with subcommands `create` (prints `export DB_...=...` lines for a long-lived shell session, e.g. a dev server + Playwright E2E run), `drop <suffix>`, `run -- <command>` (one-shot: create ephemeral `tiro_testing_<random>` schema, run the command with DB_* pointed at it, always drop on exit via `trap ... EXIT`, success or failure), and `cleanup-stale [hours]` (sweeps orphaned `tiro_testing_*` schemas from crashed/abandoned runs — found and cleaned one real orphan, `tiro_testing_suf`, left over from a prior manual one-off-name stopgap, while building this). `backend/composer.json`'s `test` script now routes through `run --` automatically, so the most common entry point (`composer test`) is isolated with zero agent awareness required. Narrow `--filter=testName` loops during active development deliberately still hit the shared default `tiro_testing` (low collision risk, fast iteration matters more there — see `backend/CLAUDE.md`'s Pest section).

**Non-obvious gotcha, verified empirically (not assumed) 2026-09-11:** Laravel's documented `--env=X` artisan flag (loads `.env.X`) does NOT reliably override `DB_DATABASE` when running under Pest/PHPUnit specifically. `runningUnitTests()` causes Laravel to auto-load `backend/.env.testing` before `--env`'s file-swap logic gets a chance to act, and phpdotenv's default immutable mode won't let a *second* file (`.env.testing_<suffix>`) override values already loaded from the *first* (`.env.testing`) — confirmed by direct test: created `.env.testing` and `.env.testing_probeC` with different DB_DATABASE markers, ran `php artisan test --env=testing_probeC`, and the `.env.testing` value won every time. What DOES work: exporting `DB_DATABASE` (and the other DB_* vars) as real OS-level process environment variables before invoking php — phpdotenv never overwrites a variable already present in the actual process environment, confirmed by the same kind of direct test (`DB_DATABASE=marker_D php artisan test ...` correctly won). This is why `test-db.sh run` passes DB_* as env-var prefixes to the child command rather than generating a per-run `.env.testing_<suffix>` file and using `--env=`.

Also discovered while validating: `backend/phpunit.xml` never set `OTP_HMAC_KEY`, causing a `CustomerAuthTest` registration-OTP failure. Added a dedicated `OTP_HMAC_KEY` to `backend/.env.testing` as a one-line fix since the file was being created anyway.

**CORRECTION (2026-09-11, later same day):** The original `226 tests, 112 passed, 18 failed` count reported alongside the above was wrong and was mischaracterized as "confirmed pre-existing/unrelated" — that conclusion was drawn from seeing the *same* failing count across two runs (wrapped and unwrapped), which only proves the failure was deterministic, not that it was pre-existing/unrelated to this file. The actual root cause of the mass failures: `.env.testing` (newly created in this same session) had no `APP_KEY=` line at all, breaking Laravel's encrypter for any test touching `encrypt()`/`decrypt()` — including `tests/Pest.php`'s own shared `actingSuperAdmin()` helper via `UserFactory::withTwoFactor()`'s `encrypt('secret')` call, which most of the suite depends on. Independently discovered/confirmed by super-admin-agent running an unmodified test file through this same `test-db.sh` wrapper. Fixed by adding a dedicated test-only `APP_KEY` (generated fresh via `php artisan key:generate --show`, not copied from `backend/.env`'s real key) to `.env.testing`, same pattern as `OTP_HMAC_KEY`. Re-ran full suite twice after the fix via `scripts/test-db.sh run -- php artisan test --compact`: both runs gave an internally consistent `226 tests, 224 passed, 2 skipped, 0 failed`, exit code 0. The 17-ish other "failures" from the original report did not actually exist as separate pre-existing bugs — they were downstream of the same missing-APP_KEY root cause. See [[feedback-validate-failure-root-cause]] for the methodology lesson.

**Why:** The user explicitly wanted a mechanism that "doesn't depend on every future agent remembering to ask" for isolation — a one-off distinct DB name per agent (the stopgap used twice already) doesn't scale. Wiring isolation into `composer test`'s default path, rather than only into a script agents have to remember to invoke, was the chosen way to make that true for the most common case.

**How to apply:** Point any full-suite Pest run or ad hoc `migrate:fresh --seed` (especially from `frontend-tester`, which needs seeded backend fixtures for E2E and has no Pest suite of its own) at `backend/scripts/test-db.sh run -- <command>` instead of running it bare. For a long-lived E2E session needing a persistent isolated DB behind a running dev server, use `eval "$(bash scripts/test-db.sh create)"` then `bash scripts/test-db.sh drop "$TIRO_TEST_DB_SUFFIX"` when done. If this script is ever modified to use `--env` instead of exported env vars again, re-verify empirically first — it was tried, it doesn't work for Pest/PHPUnit runs specifically, and that's easy to forget/relitigate without this note.
