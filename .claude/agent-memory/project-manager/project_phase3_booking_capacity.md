## Design decisions locked in this phase (durable — apply to later phases too)

- **Idempotent-secret-replay convention** (project-architect, recorded in `02-api-contract.md` + `06-open-decisions.md` item #16): when a creation endpoint issues a one-time secret that's hashed one-way at rest, but an `Idempotency-Key` replay must return the original response, use a transient **encrypted** side-cache (`Crypt::encryptString`) scoped to a short window matching the resource's own natural lifetime (here, the booking hold's 15-minute TTL) — never a long window, never plaintext. A companion boolean (`manage_token_issued`) distinguishes "never issued" from "issued but replay window closed." **Phase 4's `Order` guest-continuity token is expected to reuse this pattern unmodified.**
- **Hold-with-TTL / locking convention**: `Cache::lock()` + a shared key-naming pattern (`{domain}-hold:{...}`) + a delayed-job-plus-sweep-command pair calling one shared `releaseHold()` method, behind a `HasHold` contract. Reuse the *pattern*, not a shared polymorphic table — each domain (`Booking`, future `InventoryItem`/`Promotion`) keeps its own native hold columns.
- **RBAC standing rule** (project-architect, `07-admin-auth-permissions.md` §5): any action that mints a `User` + role assignment is gated by `roles-users.manage` regardless of which module's screen triggers it — decided by what the action does, not where it lives.
- **AuditLog convention reaffirmed**: any staff-initiated write to a customer-facing entity (here, dispatch-board `Booking` moves/cancels) must write an `AuditLog` row (`auditable_type`, `actor_id`, `before`, `after`) atomically with the mutation, reusing the existing entity — never a feature-specific audit table. This is what let Phase 6 stay able to distinguish staff reshuffles from genuine customer cancellations.

## Open, tracked follow-ups (not blockers — Phase 3 shipped GO regardless)

1. **Required fast-follow, in progress**: `TechnicianShiftRequest::after()` only rejects exact-`shift_start` duplicates, not genuine time-range overlap between two shifts for the same technician/date. qa-lead personally traced `SlotComputationService.php` and confirmed this is a **roster data-integrity gap, not a double-booking/money risk** (booking-occupancy and the lock key are both per-technician across all shifts, not shift-row-scoped) — hence non-blocking for sign-off, but a real defect worth closing before Phase 4 builds further on technician scheduling. Dispatched to backend-agent 2026-09-21 (fix `after()` to reject genuine interval overlap while still allowing legitimate back-to-back split shifts; update the existing "documents the gap" regression test in `TechnicianShiftManagementTest.php` to assert correct rejection instead).
2. **Cosmetic backlog, not urgent**: `backend/resources/js/pages/bookings/shifts/index.tsx:353` renders a raw unformatted ISO datetime in the Shifts admin Date column. `DispatchBoardController.php`'s `move()` AuditLog writes `before.slot_start` with seconds precision, `after.slot_start` without (audit content is correct, just inconsistently formatted — worth fixing before Phase 6 reporting consumes many rows in this shape). Route to whoever next touches either file.
