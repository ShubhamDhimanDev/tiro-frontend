Tracks Phase 0's customer-auth slice from `docs/architecture/08-customer-auth-otp.md` and `docs/plan/01-task-breakdown.md`. See [[repo_layout]] for doc paths and [[feedback_verify_before_trusting_memory]] for why this was re-audited from scratch on 2026-09-10.

**Design (settled 2026-09-09, not passwordless):** registration requires email+password, gated by OTP verify before activation. Post-activation, login supports two permanent independent methods: password OR OTP, customer's choice every time. Password reset reuses OTP infra. New Sanctum `customer` guard, separate from admin `User`/Fortify auth entirely.

  1. HIGH — `User` doesn't actually implement `MustVerifyEmail` (commented out) — the `verified` middleware on `routes/{web,admin,settings}.php` is a silent no-op, `email_verified_at` never gets set for staff at all.

  3. MEDIUM — timing side-channel on `password/reset/request`: skips DB insert + mail-queue dispatch entirely for unregistered emails (response body generic, response TIME isn't). Sibling `otp/request` already does equal-work-always correctly — same pattern needs applying here.

  5. LOW, NOT fixed yet, tracked as a follow-up — raw OTP codes sit in plaintext in the `jobs` table while queued and indefinitely in `failed_jobs` on delivery failure (database queue driver). Retention/purge-policy gap, not a code bug — likely resolved naturally once queue moves to Redis with real TTLs, or needs a scheduled cleanup command. **Recorded as open decision #14 in `docs/architecture/06-open-decisions.md` (added 2026-09-10, per user instruction not to let it float only in a status report) — owner still TBD (devops-agent or backend-agent), needs assigning before launch.**
  6. LOW/informational, bundled into the fix pass since cheap — OTP `code_hash` HMAC keyed on shared `APP_KEY` rather than a dedicated secret; add `OTP_HMAC_KEY` env var.
